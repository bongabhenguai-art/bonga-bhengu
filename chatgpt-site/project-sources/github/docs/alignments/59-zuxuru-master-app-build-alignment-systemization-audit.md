## Source-specific findings
The document proposes an orchestrated business growth loop: public discovery → business profile → permissioned Vault → real connected data → visibility and brand intelligence → strategy → Studio → verified execution → **Systemize** → Autopilot → repeat. It specifies:
- **Discovery and evidence:** Founding Name Visibility and DeepSearch using public websites, maps, social, directories, reviews and competitors. Example numbers such as 64/100 and 25→61 are **illustrative only**, never real metrics without source evidence and documented scoring.
- **Vault:** explicit states Available, Authorization Required, Connecting, Verifying, Syncing, Connected, Sync Error, Expired, Disconnected and Revoked; no fake connection cards.
- **Website:** existing-site path Verify→Inspect→Analyse→Recommend→Improve, missing-site path Plan→Generate→Review→Deploy→Verify→Business Graph.
- **Brand/marketing/customer/market intelligence:** share one Business Profile/Graph and feed an approved execution plan, rather than isolated dashboards.
- **Studio:** optional 5–8-camera production, six-camera reference layout, multiview, program/preview, audio, mobile uploads, transcription, content intelligence and repurposing. Real capture requires supported hardware/browser/device permissions; the diagram alone is not functional capture.
- **Systemize layer:** map actual business work, identify owner dependency, measure time/cost, design repeatable processes, allocate to human/software/AI, automate only when appropriate and measure leverage.
- **AI agent layer:** Discovery, Visibility, Website, SEO, Brand, Social, Google, Competitor, Customer, Market, Strategy, Studio, Execution, Autopilot and Systemization agents. Orchestrator selects business context, evidence, engine, agent, connector, approvals, records and next step.
- **Autopilot authority classes:** observe, recommend, require approval, authorized auto-execution, or human escalation.
- **Functional done:** actual public evidence, authorized connector sync, stored structured data, real external execution, verification and measured result; a screen/button/table alone is insufficient.
- **Proposed vendor map:** GitHub, Supabase, Logto, Netlify, Agent-Reach, OmniRoute, Postiz, ToolJet, ComfyUI are replaceable suggestions, not confirmed integrations.
- **Historical repository tree:** `zuxuru/apps/web`, packages, Supabase, etc. is a proposed target, not permission to restructure Bonga's current repository.

## Phone-like service delivery principle
A user asks by voice, chat, tap or upload for a business outcome. The existing Bonga orchestrator selects configured internal tools and AI employees, performs permitted work, stores tangible outputs and returns results. Do not force users to configure GitHub, MCP or API keys. Provider-mandated account authorization remains necessary for customer-owned external platforms; the system must not pretend otherwise.

## Conflict and duplication controls
1. The source states Zuxuru is the single product and Fukulisane its foundation. For this project, **Bonga Bhengu App is the single main product**; these names identify donor capabilities only.
2. This specification overlaps file 2's earlier master alignment and files 54–58's later build bundle. Record it as a historical variant; avoid duplicate app shells, registries or engines.
3. The source's Zuxuru-specific repository tree, Supabase/Logto recommendations and build phases are not migration orders.
4. Systemize is the notable differentiated capability: add it as an AI employee/workflow capability within Bonga's Business Coach and Execution Intelligence, not a separate paid product.
5. Public search cannot establish a private person's dossier or guarantee that a missing platform does not exist.
6. Publishing, outreach, payments and account changes require actual authority, approval policy and verifiable action receipts.
