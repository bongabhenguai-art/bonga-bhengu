# FUKULISANE ONE — MASTER CONCEPT & ARCHITECTURE FILE

## 1. Product identity
Fukulisane One is a real, live business operating ecosystem, not a prototype or demo. Its mission is to solve business digital visibility and growth using human input, real connected data, live AI processing, executable engines, workflows, integrations, and measurable outputs.

## 2. Storefront vs Admin Dashboard
### Public Storefront
Shows Fukulisane One services and customer-facing outcomes. It should not expose internal engines, orchestrators, scanners, integrations, or admin tooling as products.

### Admin Dashboard
Contains the actual operating system: engines, tools, wizards, orchestrators, scanners, integrations, workflows, audits, data, monitoring, and execution controls.

The storefront sells/explains services. The admin operates the machinery.

## 3. Non-negotiable live-system rule
Every engine, orchestrator, wizard, scanner, and integration must:
- Have a real screen.
- Accept human input.
- Connect to real data/services.
- Execute real work.
- Produce real outputs.
- Show status and errors.
- Save results.
- Be testable.

Never fabricate data to make a screen look complete. If an integration is unavailable, show it as unconnected/not assessed.

A sidebar item is not proof of functionality. A component is complete only when it executes and produces a real result.

## 4. Human + AI operating model
Human input -> AI processing -> real data -> real execution -> real output.

Always distinguish:
- Verified facts
- AI analysis
- Predictions
- Recommendations

Important findings should be traceable to evidence.

## 5. Fukulisane Deep Search AI
This is the central discovery/intelligence engine. It discovers, verifies, profiles, monitors, and analyzes:
- Businesses
- People
- Brands
- Domains
- Websites
- Products
- Customers
- Competitors
- Markets
- Suppliers
- Manufacturers
- Opportunities

Connected/authorized sources can include websites, Google/Search, Google Business Profile, social media, news, directories, reviews, CRM, CMS, ERP, analytics, sales/marketing systems, e-commerce systems, and internal Fukulisane data.

Never claim a source is live unless its real connector works.

## 6. Deep Search four-stage architecture
### Stage 1 — Search
Discover and collect verified information from the business/person/domain/product/brand/industry/keyword input.

### Stage 2 — Profile
Create structured Business, Customer, Product, Opportunity, Competitor, Brand, Supplier, and Market profiles.

### Stage 3 — Search What Is Missing / Gap Search
Find missing website content, Google presence, social activity, SEO, calls to action, campaigns, follow-up, offers, sales mechanisms, partnerships, suppliers/distribution, and other evidence-based gaps.

### Stage 4 — Generate Solutions
Turn profiles and gaps into executable branding, marketing, content, SEO, lead generation, sales, follow-up, personalized package, opportunity, and growth recommendations.

## 11. Customer Intelligence + Closer
Deep Search can discover customers who are looking for a product/service where the discovery is legally and technically available.

Customer intelligence can include evidence-supported:
- Need
- Product interest
- Budget indicators
- Buying stage/readiness
- Timing
- Decision factors
- Objections
- Communication preferences
- Relevant signals

Closer/Sales generates personalized packages based on actual need, budget, readiness, and purchase blockers.

Previously identified blockers include colour, size, distance, missing product information, availability, price/budget, and other evidence-based reasons for not buying.

If a dealer lacks a requested product, the system should be able to search connected/authorized sources, find who has it, collect product information, and create a deal strategy.

## 14. Repository Deep Scanner
Separate from Business Deep Search. This engineering scanner runs before changing the app.

Read:
- Concept files
- Specifications
- Source code
- APIs
- Database schemas
- Workflows
- Configuration
- Tests
- Deployment
- Documentation

For each component determine:
- Name
- Purpose
- Business problem solved
- Inputs
- Outputs
- Dependencies
- Implementation status
- Production readiness

Detect duplicates, similar logic, duplicate APIs/models, broken references, circular dependencies, unused services, orphan components, dead code, and missing integrations.

Search/reuse before creating.

## 15. Naming and data preservation
Do not casually rename existing components. Names are architectural references. Renaming can break references, lose context, create duplicates, and lead to wrong tools.

Read existing files according to their names/functions before changing them.

## 25. Build/audit loop
Before building:
1. Read concept/spec files.
2. Scan repository.
3. Inventory components.
4. Identify duplicates.
5. Identify reusable components.
6. Check dependencies.
7. Identify missing integrations.
8. Design implementation.

During build:
1. Preserve names.
2. Reuse existing functionality.
3. Connect real data.
4. Implement real backend behavior.
5. Add tests.
6. Execute real workflows.

After build:
1. Build.
2. Run tests.
3. Verify integrations.
4. Verify outputs.
5. Audit UI against real engine state.
6. Check for fake/placeholder data.
7. Record results.
8. Update concept files.

## 27. Master principle
Fukulisane One is not a collection of screens. It is a connected operating system of live engines.

The storefront explains services.
The admin dashboard operates machinery.
The intelligence layer discovers and verifies information.
The audit layer understands the business.
The improvement layer decides what should happen next.
The execution engines perform the work.
The data layer records what happened.
The measurement layer determines whether the work produced a real result.

Completion means:

REAL INPUT -> REAL PROCESSING -> REAL DATA -> REAL EXECUTION -> REAL OUTPUT -> VERIFIED RESULT
